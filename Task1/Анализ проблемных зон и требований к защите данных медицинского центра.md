# Анализ проблемных зон и требований к защите данных медицинского центра

## Список проблемных зон текущего состояния

### 1. Небезопасное хранение конфиденциальных данных

- **Медицинские данные** (специальная категория ПДн) хранятся в открытом виде без шифрования
- Использование **небезопасных форматов** (Excel, PDF, JPG) без защиты
- **Централизованное хранение** всех данных на общем сетевом диске
- Отсутствие **шифрования данных** как при хранении, так и при передаче

### 2. Отсутствие контроля доступа и разграничения прав

- **Любой сотрудник** с доступом к сети может открыть медкарту любого пациента
- Нет **разграничения прав доступа** к данным разной категории критичности
- Нарушение принципа **врачебной тайны** - файлы доступны даже после завершения лечения
- Отсутствие **RBAC (Role-Based Access Control)** системы

### 3. Нарушения защиты персональных данных

- **ФИО и дата рождения в названии папки пациента** - нарушение Data Minimization
- Отсутствие механизма **псевдонимизации** - невозможно использовать данные для аналитики
- Невозможность выполнить **запрос пациента на удаление данных** (right to be forgotten)
- **Дублирование персональных данных** в Excel и базах 1С

### 4. Отсутствие механизмов обеспечения целостности данных

- Нет **версионирования медкарт** - риск случайного перезаписывания или удаления важной информации
- Отсутствие **резервного копирования** и восстановления
- Нет контроля **целостности данных** и истории изменений

### 5. Архитектурные уязвимости

- **Уязвимость к шифровальщикам** (все данные централизованы)
- Различные форматы файлов усложняют автоматизацию и контроль доступа
- Отсутствие **аудита действий пользователей**
- **Незащищённые файловые базы 1С** в файловом режиме

### 6. Небезопасные процессы интеграции

- **Устаревшая OLE-интеграция** между системами
- Отсутствие **API-безопасности** и валидации данных
- **Ручной ввод данных** с высоким риском ошибок

## Список данных, требующих защиты

### Высокий риск (Красный): Особо чувствительные данные

| Категория данных | Примеры | Способы защиты |
|------------------|---------|----------------|
| **Медицинская история** | Диагнозы, жалобы и симптомы, анамнез | Шифрование (AES-256), строгий RBAC, Need-to-know доступ |
| **Результаты анализов** | Лабораторные исследования, анализы, снимки | Шифрование, изоляция данных, контроль версий |
| **Удостоверения личности** | Скан паспорта, документы пациента | Шифрование, маскирование, ограниченный доступ |
| **Назначения и рекомендации** | Лечебные назначения, рекомендации врачей | Шифрование, аудит доступа |

### Средний риск (Оранжевый): Персональные данные (PII)

| Категория данных | Примеры | Способы защиты |
|------------------|---------|----------------|
| **Основные PII** | ФИО, дата рождения, телефон, email, адрес | Шифрование, маскирование (XX XXX XXX), RBAC |
| **Банковские реквизиты** | Реквизиты сотрудников для зарплаты | Шифрование, токенизация, ограниченный доступ |
| **Контакты пациентов** | Телефон, email для уведомлений | Шифрование, контроль использования |

### Низкий риск (Синий): Бизнес-данные

| Категория данных | Примеры | Способы защиты |
|------------------|---------|----------------|
| **Расписание врачей** | График работы, дата/время приёма | RBAC, мониторинг доступа |
| **Учёт ТМЦ** | Наименование, количество, стоимость ТМЦ | Шифрование, контроль изменений |
| **Финансовые операции** | Суммы платежей, бухгалтерские проводки | Шифрование, аудит операций |

## Способы защиты данных

### Шифрование

- **AES-256** для данных на rest (в хранилищах)
- **TLS 1.3** для данных in transit (при передаче)
- **Шифрование баз данных** пациентов, документов, финансовых данных
- **Шифрование объектных хранилищ** для сканов и документов

### Контроль доступа

- **RBAC (Role-Based Access Control)** система
- **IAM (Identity and Access Management)** централизованная аутентификация
- **Need-to-know принцип** - минимально необходимый доступ
- **Изоляция данных** между пациентами и сотрудниками

### Анонимизация и псевдонимизация

- **Псевдонимизация** для аналитики и BI/ML/AI систем
- **Обезличивание** агрегированных данных для Data Lake
- **Маскирование** данных при отображении (XX XXX XXX для номеров)
- **Токенизация** финансовых данных

### Мониторинг и аудит

- **Сквозной аудит** всех действий пользователей
- **Неизменяемые логи действий** для полного трейсинга
- **Мониторинг несанкционированного доступа**
- **Агрегирование логов** в систему мониторинга

### Целостность и доступность

- **Git-like версионирование** через Nessie Data Catalog
- **Автоматическое резервное копирование** и восстановление
- **Контроль версий** для медицинских карт и назначений
- **Распределённое хранение** для защиты от шифровальщиков

## Механизм тегирования данных

### Инструменты тегирования

- **Nessie Data Catalog** - основной инструмент для версионирования и тегирования метаданных
- **Встроенные механизмы СУБД** для тегирования на уровне базы данных
- **Метаданные в объектных хранилищах** для документов и файлов

### Схема тегирования через Nessie

| Тег данных | Категория | Уровень конфиденциальности |
|------------|-----------|----------------------------|
| `MED_SENSITIVE` | Медицинские данные | `confidentiality:critical` |
| `PD_PERSONAL` | Персональные данные | `confidentiality:high` |
| `FIN_PRIVATE` | Финансовые данные | `confidentiality:high` |
| `INTERNAL` | Служебные данные | `confidentiality:medium` |
| `METADATA` | Метаданные операций | `confidentiality:low` |

### Реализация тегирования в архитектуре TO-BE

- **Автоматическое тегирование** на уровне бизнес-сервисов (Сервис пациентов, Сервис документов)
- **Версионирование тегов** через Nessie Data Catalog
- **Политики доступа на основе тегов** - Nessie предоставляет политики сервисам
- **Git-like управление** тегами и классификацией данных

### Преимущества использования Nessie для тегирования

- **Сквозное версионирование** изменений в тегах и классификации
- **Единый каталог** для всех типов данных (PII, медицинские, финансовые)
- **Автоматическое применение политик** безопасности на основе тегов
- **Полная история изменений** классификации данных для compliance

## Архитектурные решения TO-BE

### Ключевые компоненты безопасности

1. **API Gateway (TLS 1.3)** - защита всех внешних интерфейсов
2. **IAM Система (RBAC)** - централизованное управление доступом
3. **Сервис пациентов (шифрование)** - защита PII данных
4. **Сервис документов (шифрование)** - защита медицинских документов
5. **Nessie Data Catalog** - версионирование и тегирование
6. **Система мониторинга** - аудит и алертинг

### Принципы безопасности

- **Zero Trust архитектура** - проверка каждого запроса
- **Data Minimization** - сбор только необходимых данных
- **Privacy by Design** - защита конфиденциальности на уровне архитектуры
- **Defense in Depth** - многоуровневая защита данных

## Соответствие регуляторным требованиям

### 152-ФЗ (Защита персональных данных)

- **Шифрование ПДн** при хранении и передаче
- **Разграничение доступа** к персональным данным
- **Аудит обработки ПДн** - полное логирование действий
- **Право на удаление** - реализация механизма "right to be forgotten"

### Медицинские стандарты (врачебная тайна)

- **Изоляция медицинских данных** от несанкционированного доступа
- **Соблюдение принципа врачебной тайны** - ограничение доступа после лечения
- **Защита специальных категорий ПДн** - медицинская информация

### Финансовые требования

- **PCI DSS совместимость** для платежных данных
- **Защита финансовой информации** сотрудников
- **Аудит финансовых операций** - полная отслеживаемость
