# Стратегия защиты данных

## 1. Классификация данных

| Категория данных | Примеры | Чувствительность | Профиль риска | Состояние | Обоснование защиты |
|------------------|---------|------------------|---------------|-----------|-------------------|
| **Особо чувствительные медицинские данные** | Диагнозы, истории болезней, результаты анализов, сканы документов | Критическая | Высокий | At rest, in transit, in use | 152-ФЗ (специальные категории ПДн), врачебная тайна, GDPR |
| **Персональные данные (PII)** | ФИО, дата рождения, телефон, email, адрес | Высокая | Высокий | At rest, in transit, in use | 152-ФЗ, риск реидентификации пациентов |
| **Финансовые и бухгалтерские данные** | Платежи, реквизиты, зарплатные ведомости | Высокая | Высокий | At rest, in transit, in use | PCI DSS, финансовая отчетность |
| **Метаданные и системные данные** | Логи действий, теги конфиденциальности, политики доступа | Средняя | Средний | At rest, in transit, in use | Аудит безопасности, compliance |
| **Бизнес-данные** | Расписание врачей, записи на прием | Низкая | Низкий | At rest, in transit, in use | Бизнес-непрерывность |

## 2. Инструменты защиты данных

### 2.1 Защита данных At Rest (в покое)

| Категория данных | Инструменты защиты | Технологии из TO-BE |
|------------------|-------------------|---------------------|
| **Медицинские данные** | Шифрование на уровне БД, контроль версий | Шифрование в patient_db, версионирование через Nessie |
| **PII данные** | Шифрование столбцов, псевдонимизация | Шифрование в patient_db, анонимизация для Data Lake |
| **Документы** | Шифрование файлового хранилища | Шифрование в document_store |
| **Метаданные** | Шифрование БД метаданных | Шифрование в metadata_db |
| **Логи аудита** | Неизменяемое хранилище логов | audit_logs с защитой от изменений |

### 2.2 Защита данных In Transit (в передаче)

| Направление передачи | Инструменты защиты | Технологии из TO-BE |
|---------------------|-------------------|---------------------|
| **Внешние подключения** | TLS 1.3, API Gateway | API Gateway с TLS 1.3 |
| **Внутренняя коммуникация** | mTLS между сервисами | SSL между микросервисами |
| **Интеграция с лабораториями** | API Key + TLS | lab_integration с валидацией контрактов |

### 2.3 Защита данных In Use (при использовании)

| Сценарий использования | Инструменты защиты | Технологии из TO-BE |
|---------------------|-------------------|---------------------|
| **Просмотр медицинских карт** | Динамическое маскирование данных, водяные знаки | RBAC в IAM System, политики минимального доступа |
| **Обработка данных врачами** | Изоляция сессий, временные токены доступа | Сессионное управление в портале сотрудников |
| **Аналитика и отчетность** | Агрегация данных, ограничение выборок | Сервис анонимизации, Data Lake с защищенным доступом |
| **Работа с документами** | Предпросмотр без скачивания, цифровые водяные знаки | Secure viewer в document_service |
| **API запросы** | Ограничение частоты запросов, квотирование | Rate limiting в API Gateway |

## 3. Автоматизированный контроль

### 3.1 Системы мониторинга и контроля

- **Nessie Data Catalog** - автоматическое тегирование и версионирование метаданных
- **RBAC через IAM System** - динамический контроль доступа на основе ролей
- **Аудит действий** - мониторинг всех операций с чувствительными данными
- **Автоматическая классификация** - тегирование данных по уровню конфиденциальности

### 3.2 Политики автоматизации

Система автоматически применяет следующие настройки безопасности для разных типов данных:

**Для медицинских данных (диагнозы, анализы, истории болезней):**

- Обязательное шифрование при хранении
- Хранение не более 5 лет
- Полное логирование всех обращений к данным
- Автоматическое обезличивание перед отправкой в аналитику
- Ограничение одновременного доступа к данным

**Для персональных данных (ФИО, телефоны, email):**

- Обязательное шифрование
- Замена идентификаторов на псевдонимы при обработке
- Поддержка права пациента на удаление своих данных
- Маскирование при отображении в интерфейсах

**Для финансовых данных (платежи, реквизиты):**

- Обязательное шифрование
- Полная история всех операций с данными
- Строгий контроль доступа
- Валидация операций в реальном времени

## 4. Реестр средств защиты

### 4.1 Программные средства

| Категория | Решения | Назначение в системе |
|-----------|---------|---------------------|
| **Шифрование** | Встроенное шифрование БД, TLS 1.3 | Защита patient_db, document_store, API Gateway |
| **Управление доступом** | IAM System (RBAC) | Централизованный контроль прав доступа |
| **Версионирование** | Nessie Data Catalog | Git-like контроль изменений метаданных |
| **Мониторинг** | Система мониторинга + аудит логов | Полный аудит действий пользователей |
| **Анонимизация** | Сервис анонимизации | Подготовка данных для Data Lake |
| **Защита при использовании** | Динамическое маскирование, сессионный контроль | Защита данных во время работы пользователей |

### 4.2 Аппаратные средства

| Категория | Решения | Обоснование |
|-----------|---------|-------------|
| **HSM модули** | Для хранения корневых ключей | Защита мастер-ключей шифрования |
| **Серверы мониторинга** | Выделенные хосты для аудита | Изоляция систем безопасности |

## 5. Реализация в архитектуре

### 5.1 Уровни защиты

1. **Периметровый уровень** - API Gateway с TLS 1.3
2. **Сервисный уровень** - mTLS между микросервисами  
3. **Уровень данных** - Шифрование БД и хранилищ
4. **Уровень использования** - Контроль сессий и маскирование данных
5. **Аналитический уровень** - Автоматическая анонимизация

### 5.2 Ключевые механизмы

- **Шифрование "по умолчанию"** - все данные шифруются автоматически
- **Минимальные привилегии** - RBAC с принципом need-to-know
- **Сквозной аудит** - полная трассировка доступа к данным
- **Автоматическое тегирование** - классификация по чувствительности
- **Защита в реальном времени** - контроль доступа во время использования данных

## 6. Соответствие требованиям

### 6.1 Нормативные требования

- **152-ФЗ** - через шифрование ПДн и медицинских данных
- **Врачебная тайна** - через строгий контроль доступа и аудит
- **GDPR** - через право на удаление и анонимизацию
- **PCI DSS** - через защиту финансовых транзакций

### 6.2 Принципы Privacy by Design

- **Proactive not Reactive** - защита встроена в архитектуру
- **Privacy as Default** - минимальный доступ по умолчанию
- **End-to-End Security** - сквозное шифрование
- **Visibility & Transparency** - полный аудит операций
- **Protection During Usage** - защита данных во время использования

## 7. План внедрения

### 7.1 Этап 1: Базовая защита

- Включение шифрования в БД пациентов и документов
- Настройка TLS 1.3 на API Gateway
- Развертывание IAM системы

### 7.2 Этап 2: Расширенная защита

- Внедрение Nessie для версионирования метаданных
- Настройка системы мониторинга и аудита
- Реализация сервиса анонимизации

### 7.3 Этап 3: Защита при использовании

- Внедрение динамического маскирования данных
- Настройка сессионного контроля доступа
- Реализация защиты данных в реальном времени

### 7.4 Этап 4: Автоматизация

- Настройка автоматического тегирования данных
- Внедрение политик автоматического удаления
- Интеграция систем контроля доступа
